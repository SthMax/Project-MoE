## 1. 实验目标与定位

### 1.1 本实验的定位

| 维度 | 说明 |
|------|------|
| **实验性质** | MVP（Minimum Viable Product）+ 验证性实验 |
| **理论对应** | `Model/PriceMoE_Final_Model_v2.1.md` 中的 PriceMoE 路由策略 |
| **代码基础** | 基于 E1.1 已有的 `moe_stats.py` 统计框架扩展 |
| **目标期刊** | 验证 MS/OR 论文中的核心声明 |

### 1.2 实验目标

**核心目标**：验证 PriceMoE 的拥塞惩罚机制（$\tilde{s}_{ce} = s_{ce} - \alpha \cdot q_e$）能否：
1. **降低专家负载不均衡**（max-load/mean-load 比值下降）
2. **提升高并发下的吞吐量**（tokens/s 提升）
3. **控制质量损失在可接受范围内**（PPL 上升 < 5%）

**次要目标**：
- 验证 EMA 平滑机制的稳定性（避免震荡）
- 探索 $\alpha$ 参数的最优范围
- 为后续 Scheduler 集成和完整版本打下基础

### 1.3 与 Chat Log 原始设想的更新

| 原始设想 | 更新后的规划 | 原因 |
|---------|-------------|------|
| "Queue length" 定义模糊 | 明确定义为 **Virtual Queue**：batch 内被路由到该专家的 token 数 | 符合 vLLM 架构（无真实队列） |
| 同时考虑通信惩罚 $\gamma$ | MVP 阶段**只实现拥塞惩罚 $\alpha q_e$** | 通信惩罚需 kernel 级修改，工作量过大 |
| 质量约束 $(1-\epsilon)\max$ | 改为**事后监控 Divergence**，按需添加 | 简化实现，先验证核心思想 |
| 需要修改 Scheduler | MVP **不修改 Scheduler**，仅在 Router 层实现 | 降低风险，保持架构兼容 |

## 2. 核心理论回顾

### 2.1 PriceMoE 路由策略（来自 v2.1 模型）

**修正评分公式**：
$$\tilde{s}_{c,e}(t) = s_{c,e} - \alpha \cdot q_e(t)$$

**路由规则**：
$$e^*(c,t) \in \arg\max_{e \in \mathcal{A}_c} \tilde{s}_{c,e}(t)$$

其中：
- $s_{c,e}$：原始 gating logits（Router 输出）
- $q_e(t)$：专家 $e$ 的虚拟队列长度
- $\alpha > 0$：拥塞惩罚系数（可调超参）
- $\mathcal{A}_c$：token $c$ 的允许专家集合（Top-k 候选）

### 2.2 虚拟队列定义（关键创新）

根据 `Model_Coding_Version.md` 和 vLLM 架构理解：

**定义**（Batch 内虚拟队列）：
$$q_e(t) := \sum_{j \in \mathcal{B}(t)} \mathbb{I}\{e \in \text{Routed}(j)\}$$

即当前 batch 内被路由到专家 $e$ 的 token 数量。

**跨 Batch 平滑**（EMA）：
$$\hat{q}_e^{(t+1)} = (1 - \rho) \cdot \hat{q}_e^{(t)} + \rho \cdot q_e(t)$$

其中 $\rho \in (0,1)$ 为平滑系数（建议初始值 0.1）。

### 2.3 物理意义

$q_e(t)$ 不是真正的"等待队列"，而是**拥塞程度的度量**：
- $q_e(t)$ 高 → 专家 $e$ 是热门专家 → 该专家是瓶颈
- $q_e(t)$ 低 → 专家 $e$ 利用率低 → 有冗余容量

**关键洞察**（来自 Chat/260123 Implementation Problems.md）：
> 在 MoE 推理中没有"token 排队等待专家"的概念。热门专家不会让 tokens "排队"，而是让**该 batch 的计算时间变长**（瓶颈效应）。

## 3. 实验设计

### 3.1 实验分组

| 分组 | 路由策略 | 说明 |
|------|---------|------|
| **Baseline** | 原始 Top-k | vLLM 默认行为 |
| **PriceMoE-$\alpha$** | $\tilde{s} = s - \alpha q$ | 多个 $\alpha$ 值扫描 |

建议 $\alpha$ 扫描范围：`[0.01, 0.05, 0.1, 0.2, 0.5, 1.0]`

### 3.2 实验变量

**自变量**：
1. $\alpha$：拥塞惩罚系数
2. $\rho$：EMA 衰减率（可固定为 0.1，或作为消融变量）
3. 并发度：`concurrency ∈ {1, 4, 8, 16, 32}`

**控制变量**：
- 模型：Qwen3-30B-A3B（或 Qwen3-Next-80B-A3B）
- TP：4（固定）
- `max_model_len`：4096（或 8192）
- `max_num_seqs`：与并发度匹配

**因变量**：
- 吞吐量（tokens/s）
- 延迟（p50, p95, p99）
- PPL（Perplexity）
- 专家负载不均衡度

### 3.3 实验矩阵

```
对于每个 (model, alpha, concurrency) 组合：
    1. 运行吞吐量测试（固定请求数 N=1000）
    2. 收集路由统计（专家负载分布）
    3. 计算 PPL（在 wikitext 子集上）
```

### 3.4 对照实验：E1.2 作为前置依赖

实验 1.3 依赖 E1.2（改变 top-k 观察质量-稀疏度曲线）的结果：
- 如果 E1.2 表明"减少 top-k 对质量影响有限"，则 PriceMoE 的路由调整风险更低
- 如果 E1.2 表明"减少 top-k 质量损失明显"，则需要更保守的 $\alpha$ 值

### 4.2 核心修改：PriceMoERouter 实现

**文件**：`vllm/model_executor/layers/fused_moe/price_moe_router.py`（新增）

```python
# price_moe_router.py (MVP 版本草案)

import torch
from vllm.model_executor.layers.fused_moe.fused_moe_router import FusedMoERouter
from vllm.model_executor.layers.fused_moe.config import RoutingMethodType


class PriceMoERouter(FusedMoERouter):
    """
    PriceMoE 路由策略：基于影子价格的拥塞感知路由。
    
    核心公式：s̃_{ce} = s_{ce} - α · q_e(t)
    
    参数:
        alpha: 拥塞惩罚系数（推荐范围 0.01-1.0）
        ema_decay: EMA 衰减率（推荐 0.9）
        top_k: Top-k 专家数
        renormalize: 是否对权重归一化
        global_num_experts: 全局专家数
    """
    
    def __init__(
        self,
        alpha: float = 0.1,
        ema_decay: float = 0.9,
        top_k: int = 8,
        renormalize: bool = True,
        global_num_experts: int = 64,
        **kwargs
    ):
        super().__init__()
        self.alpha = alpha
        self.ema_decay = ema_decay
        self.top_k = top_k
        self.renormalize = renormalize
        self.global_num_experts = global_num_experts
        
        # 专家负载统计（virtual queue）
        # 注意：必须放在 GPU 上，避免 CPU-GPU 同步开销
        self._expert_load: torch.Tensor | None = None
    
    @property
    def routing_method_type(self) -> RoutingMethodType:
        return RoutingMethodType.PRICE_MOE  # 需要在 config.py 中添加
    
    def _get_or_init_expert_load(self, device: torch.device) -> torch.Tensor:
        """懒初始化专家负载张量"""
        if self._expert_load is None or self._expert_load.device != device:
            self._expert_load = torch.zeros(
                self.global_num_experts,
                dtype=torch.float32,
                device=device
            )
        return self._expert_load
    
    def select_experts(
        self,
        hidden_states: torch.Tensor,
        router_logits: torch.Tensor,
    ) -> tuple[torch.Tensor, torch.Tensor]:
        """
        PriceMoE 路由：修正评分 → Top-k 选择 → 更新负载统计
        
        Args:
            hidden_states: (T, D) 输入 token embeddings
            router_logits: (T, E) 原始 gating scores
            
        Returns:
            (topk_weights, topk_ids): 权重和专家 ID
        """
        T, E = router_logits.shape
        device = router_logits.device
        
        # 1. 获取/初始化专家负载
        expert_load = self._get_or_init_expert_load(device)
        
        # 2. 计算拥塞惩罚
        congestion_penalty = self.alpha * expert_load.unsqueeze(0)  # (1, E)
        
        # 3. 修正评分
        adjusted_logits = router_logits - congestion_penalty  # (T, E)
        
        # 4. Top-k 选择
        topk_weights, topk_ids = torch.topk(
            adjusted_logits,
            k=self.top_k,
            dim=-1
        )  # (T, k), (T, k)
        
        # 5. 归一化权重（可选：用原始 logits 或调整后的 logits）
        # 策略 S（推荐）：用原始 logits 归一化，保持质量
        if self.renormalize:
            # 从原始 router_logits 中提取选中专家的分数
            original_scores = torch.gather(router_logits, 1, topk_ids)  # (T, k)
            topk_weights = torch.softmax(original_scores, dim=-1)
        
        # 6. 更新专家负载（EMA）
        # 注意：这一步必须在 GPU 上完成，不能有 CPU 同步
        with torch.no_grad():
            counts = torch.bincount(
                topk_ids.flatten().to(torch.int64),
                minlength=E
            ).float()  # (E,)
            self._expert_load = (
                self.ema_decay * self._expert_load + 
                (1 - self.ema_decay) * counts
            )
        
        return topk_weights, topk_ids.to(torch.int32)
    
    def reset_stats(self):
        """重置专家负载统计（用于新的推理会话）"""
        if self._expert_load is not None:
            self._expert_load.zero_()
```

### 4.5 EP（Expert Parallelism）兼容性

根据 Chat/260123 Implementation Problems.md 的讨论，在 EP 模式下需要同步 `expert_load`：

```python
def _sync_expert_load_across_ep_group(self):
    """在 EP 模式下同步专家负载（可选，MVP 可暂不实现）"""
    from vllm.distributed import get_ep_group
    
    ep_group = get_ep_group()
    if ep_group is None or ep_group.world_size == 1:
        return  # 单机或无 EP
    
    # All-reduce 同步负载（开销极小：仅 E 个 float）
    torch.distributed.all_reduce(
        self._expert_load,
        op=torch.distributed.ReduceOp.SUM,
        group=ep_group.device_group
    )
```

**MVP 阶段建议**：暂不实现 EP 同步，仅在 TP-only 配置下测试。

## 6. 评估指标体系

### 6.1 核心指标（必须测量）

| 指标 | 定义 | 期望变化 |
|------|------|---------|
| **吞吐量** | tokens/s (mean) | ↑ 5-20%（高并发） |
| **P95 延迟** | 95th percentile latency | ↓ 10-30% |
| **PPL** | $\exp(\text{mean}(-\log p))$ | ↑ < 5% |
| **负载不均衡度** | $\max_e q_e / \text{mean}_e q_e$ | ↓ 显著 |

### 6.2 辅助指标（诊断用）

| 指标 | 定义 | 用途 |
|------|------|------|
| **Gini 系数** | 专家负载的 Gini 指数 | 量化不均衡程度 |
| **Routing Drift** | 与 Baseline 的 Jaccard 距离 | 监控路由变化幅度 |
| **Top-1 命中率** | 原始 Top-1 是否仍被选中 | 质量保守性指标 |
| **Expert 切换率** | 跨 batch 的专家选择稳定性 | 验证 EMA 效果 |

### 6.3 指标计算方法

```python
    temperature=0.0

# 计算 PPL
log_probs = [sum(t.logprobs.values()) for t in output.prompt_logprobs if t]
```

```python
def compute_load_imbalance(expert_load: np.ndarray) -> dict:
    """计算专家负载不均衡度指标"""
    mean_load = np.mean(expert_load)
    max_load = np.max(expert_load)
    
    return {
        "max_to_mean": max_load / mean_load,
        "cv": np.std(expert_load) / mean_load,  # 变异系数
```

## 8. 风险与缓解策略

### 8.1 技术风险

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|-------|------|---------|
| **路由震荡** | 中 | 质量崩塌 | 使用 EMA 平滑；调小 $\alpha$ |
| **PPL 上升过大** | 中 | 无法发表 | 保守策略（用原始 logits 归一化）；添加质量约束 |
| **吞吐无提升** | 低 | 核心假设失效 | 检查瓶颈是否在 MoE 层；增加并发度 |
| **与 EPLB 冲突** | 低 | 功能失效 | 暂时禁用 EPLB；后续兼容 |
| **EP 模式不工作** | 中 | 限制适用范围 | MVP 仅在 TP-only 测试；后续添加同步 |

### 8.2 工程风险

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|-------|------|---------|
| **vLLM 版本兼容** | 中 | 代码需重写 | 固定 vLLM commit；使用环境变量开关 |
| **性能开销过大** | 低 | 抵消收益 | 所有操作在 GPU 完成；避免 CPU 同步 |
| **统计不准确** | 低 | 结论无效 | 添加 sanity check（计数守恒） |

### 8.3 质量保障措施

**必须的 Sanity Check**：
1. **计数守恒**：$\sum_e \text{cnt\_topk}[l,e] = \text{tokens}[l] \times k$
2. **负载单调**：启用 PriceMoE 后，max-load/mean-load 应下降
3. **PPL 对比**：与 Baseline 的 PPL 差异应在预期范围内
4. **稳定性**：多次运行结果一致
