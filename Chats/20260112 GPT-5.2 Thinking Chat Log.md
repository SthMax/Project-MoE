## 1) 你到底要观察什么（建议先把观测量定义清楚）

对每一层 MoE（每个 MoE block）至少记录这些：

* **router logits / routing probs**：路由器对每个 token 的专家打分与 softmax 后概率（可以看“自信度/熵/边际”）
    
* **Top-k 选择**：每个 token 最终选了哪些专家（top-1 / top-2），以及权重
    
* **负载（load）与溢出（overflow）**
    
    * 每层每个 expert 吃到的 token 比例（utilization）
        
    * capacity 约束下的 overflow / drop（不同框架实现略有差异）
        
* **路由稳定性**：同一输入在不同 checkpoint、不同 batch、不同温度/噪声下 routing 是否稳定（Jaccard/一致率）
    
* **“专家语义”/专精（specialization）**：被某个 expert 接收的 token/片段有什么共同特征（词类、主题、语言、代码/数学符号、位置等）
    

这些指标后面都能直接支持你写出像样的结论（比如“router collapse 发生在哪些层”“哪类输入触发某些专家”“负载均衡损失是否真的改变了分布”等）。

## 2) 三类实验设计（从容易到深入）

### A. 推理侧观测：用预训练 MoE 做“路由行为学”

目标：先回答“**它现在到底怎么路由**”。

**做法**

1. 选一个开源 MoE（比如 Mixtral）。Mixtral 官方介绍明确是“每层每 token 选 2 个 experts”的路由模式。[Mistral AI+1](https://mistral.ai/news/mixtral-of-experts?utm_source=chatgpt.com)
    
2. 跑一组 **对照输入集**：
    
    * 自然语言（新闻/对话）
        
    * 代码（Python/CUDA）
        
    * 数学（公式/证明风格）
        
    * 多语言（中英混合等）
        
3. 记录每层的 router logits / top-k expert id / 权重，然后做统计和可视化：
    
    * 每层 utilization heatmap（layer × expert）
        
    * router entropy 分布（是否过于尖锐导致 collapse）
        
    * top-1 与 top-2 的 margin（自信度）
        
    * 不同输入域的 routing 差异（domain shift）
        

**用什么框架最省事**

* **Hugging Face Transformers**：可以直接让模型返回 router logits（用于算 router loss / 分析），官方文档里有 `output_router_logits` 说明。[Hugging Face+1](https://huggingface.co/docs/transformers/v4.44.0/en/model_doc/mixtral?utm_source=chatgpt.com)
    
* 另外 HF 社区也有明确回答：把 `model.config.output_router_logits = True` 就能拿到 router logits。[Hugging Face](https://huggingface.co/mistralai/Mixtral-8x7B-Instruct-v0.1/discussions/113?utm_source=chatgpt.com)
    

> 小坑：`generate()` 的输出不一定包含 router_logits（社区里有人踩过），你可以用“手写 decode loop”（每步 forward 一次）来拿到每步的 router logits。[GitHub+1](https://github.com/huggingface/transformers/issues/31722?utm_source=chatgpt.com)

* * *

### B. 受控干预：动路由超参，看行为怎么变

目标：回答“**路由机制的关键旋钮是什么**”。

建议做这些干预（每次只改一个变量）：

1. **top-k：1 vs 2**
    

* top-1 更容易出现 load 不均衡/专家闲置；top-2 往往更稳但通信/计算更重（token 复制）。
    
* DeepSpeed MoE 明确支持 `k=1 or k=2` 的 top-k gating。[DeepSpeed Documentation+1](https://deepspeed.readthedocs.io/en/stable/moe.html?utm_source=chatgpt.com)
    

2. **capacity_factor / eval_capacity_factor**（容量约束）
    

* 观察 overflow/drop 比例 vs perplexity/准确率 vs 训练稳定性
    
* DeepSpeed MoE 也把这些作为关键参数暴露出来。[DeepSpeed Documentation](https://deepspeed.readthedocs.io/en/stable/moe.html?utm_source=chatgpt.com)
    

3. **router logits temperature / normalization / jitter noise**
    

* 温度越低路由越尖锐（更易 collapse），越高更均匀但可能损失专精
    
* 你可以直接对 logits 做 temperature scaling（无需改模型结构）来做因果对照
    

4. **aux loss / router z-loss**
    

* HF 的 MoE 介绍里提到 router z-loss 用于稳定训练（惩罚过大的 logits）。[Hugging Face+1](https://huggingface.co/blog/moe?utm_source=chatgpt.com)
    
* Transformers 里也有 load balancing loss 的实现思路（以 gate logits → top-k → one-hot mask → 统计均衡为核心）。[GitHub](https://github.com/huggingface/transformers/issues/28093)
    

* * *

### C. 训练动态：从“观察”走向“解释为什么”

目标：回答“**router 在训练中怎么学会分工、什么时候崩、怎样救**”。

我建议你至少做一个 **toy 级 MoE 训练**（小模型 + 小数据子集），记录全程曲线：

* utilization 的 entropy / CV（变均匀还是变塌缩）
    
* aux loss 与主 loss 的相互作用（是否出现“aux loss 压不住”）
    
* 专家权重相似度随时间变化（专家是否分化，还是学成一堆相似 FFN）
    
* routing 稳定性随训练推进（早期大幅摆动，后期收敛？）

## 2) 你们 4×40GB 到底能不能把它跑起来？

### 结论（直白版）

* **80B bfloat16 / fp16 原权重：基本“卡线”，很容易启动就 OOM，或一加长输入就崩。**
    
* **FP8/8bit 这类“权重压缩版”：可跑，并且更适合你做 routing 大规模统计。**
    

### 为什么 bf16 原版在你们机器上很危险？

HF 上有很明确的回答：这模型**仍然需要把整个 80B 权重装进 VRAM**；不量化的话权重约 **160GB**，而且“实践中通常需要更多（取决于你要的 context 长度）”。[Hugging Face](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct/discussions/7)

你们总显存正好 160GB，但运行时还要：

* KV cache / 其他缓存
    
* kernel workspace、CUDA graph、allocator 碎片
    
* 并行通信 buffer 等
    

所以 **“恰好等于”≈“大概率不稳”**：可能需要把 `--gpu-memory-utilization` 拉得很极限才启动，且长输入不稳（HF 讨论里也有人类似情况）。[Hugging Face](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct/discussions/7)

### B) 你做 routing 研究，“FP8 会不会影响结论”？

## 4) 能做哪些“routing 实验”？你们机器能支撑到什么深度？

我把实验分三档，你可以对照选：

### 档 1：观测型（强烈推荐，最适配你目标）

**目标：给 fluid approximation 提供真实 arrival-rate / load 分布。**  
做法：跑模型推理，打开/记录每层 router 输出（logits/probs/top-k），做统计。

在 Transformers 里，Qwen3-Next 文档明确支持 `output_router_logits` 用来返回各层 router logits（用于 router loss 之类）。[Hugging Face](https://huggingface.co/docs/transformers/en/model_doc/qwen3_next?utm_source=chatgpt.com)  
你可以据此做：

* token→expert 的到达率（per layer / per domain）
    
* 负载分布尾部（heavy hitter experts）
    
* router entropy / margin（不确定性）
    
* 跨层相关（同一 token 在不同层是否“专家路径”稳定）
    
* 512 专家的“热度 rank-frequency”（对你做流体极限很关键）
    

这类实验**完全可以在 4×A100 上落地**，尤其用 FP8/8bit 权重。

### 档 2：推理期“受控干预”（有限但能做）

你说的“各种 routing 实验”，如果指 **改变 top-k、容量、噪声、温度** 等：

* **不改权重、只改选择规则（post-hoc re-routing）**：  
    你可以用 router logits 重新采样/重排 top-k，做“如果路由规则变了，负载会怎样”的反事实分析。  
    优点：省算力、非常适合 fluid approximation。缺点：不等价于真实 forward（因为专家输出没跟着变）。
    
* **改 forward（真的让 token 走不同专家）**：  
    这就会显著增加工程和算力压力，但在“小 batch/短上下文”下仍可做一些验证性实验（比如只改某一两层、只看局部指标）。
    

### 档 3：训练动态/重训 router（基本不现实）

如果你想“训练中观察 collapse / 专家分工形成过程”，80B 级别在 4×40GB 上**基本不可行**（即使只训 router，也要保留大量激活、还要做反传，显存/吞吐都不够）。  
建议用更小的 MoE（同样大 E、小 hidden）复现机制，再把“观测型统计”迁移到 80B 上验证。

# 实验 1.1：多数据集观察 expert activation 分布（“arrival process 长什么样”）

### 目标

给 fluid approximation 提供最关键的输入：**每层每 expert 的到达率/负载分布**，以及它如何随数据域变化。

### 数据集建议（选 4 类就够写 paper）

* **General text**：WikiText-103 / C4 子集
    
* **Code**：MBPP / HumanEval prompts（或你们内部 code corpus）
    
* **Math/Reasoning**：GSM8K（只用题目部分）/ MATH 子集
    
* **Multilingual**：Flores-200 子集 / 中英混合语料
    

每类先取一个“轻量版”：比如 1k～5k 段，每段截到固定 token 长度（例如 512 或 1024），保证统计可比。

### 运行模式（推荐“teacher-forcing 的 prefill-only”）

* 对每段文本，喂给模型做 **prompt logprobs**（不生成），拿到 token logprob 只是为了后续 ppl；routing 统计来自你在 MoE router 里插桩得到的 top-k indices。
    

### 你要记录的统计量（paper 图表直接用）

对每个 MoE layer（48 层）：

1. **Load heatmap**：`load[l,e] = count[l,e] / sum_e count[l,e]`
    
2. **不均衡度**：Gini / CV / max-to-mean ratio / entropy
    
3. **top-p expert 占比**：比如 top-1%、top-5% experts 吃掉多少 token
    
4. **域间相似度**：同一 layer 的 `load` 在不同数据集之间做 cosine/JSD，证明“路由对 domain 有响应”
    
5. （可选）**co-activation**：top-k 里 expert pair 的共现矩阵（看是否存在“专家簇”）
    

### 工程实现建议（vLLM）

* 在 `FusedMoERouter.select_experts`（或等价位置）里拿到 `topk_indices` 后直接 `bincount` 聚合。
    
* 注意：你们的模型是 **E=512、k=10(+shared)**，聚合数组规模是 `48×512`，非常小。
    
* **不要**把 logits 全存下来；如果你确实需要 margin/entropy，只抽样 0.1% token 存 logits 统计分位数即可。

# 实验 1.2：改变 top-k，观察 perplexity 与 benchmark（“质量-稀疏度曲线”）

### 目标

证明：**路由稀疏度（top-k）确实带来可量化的性能差距**，并给你后面“加 cost”提供对照基线。

### 关键点：Qwen3-Next 训练时是 top-10(+shared)，你只能安全地“减 k”

建议测试：`k ∈ {1,2,4,8,10}`（shared expert 始终保留）。

### 路由实现的两个版本（强烈建议都做）

* **Version A（更保守）**：只用原 router logits 选 top-k，然后对选中的 k 个 expert **重新 softmax 归一化权重**（shared 单独加回）。
    
* **Version B（更“贴近训练”）**：先按原本 top-10 得到权重，再把其中非前 k 的权重置 0，然后对剩余权重 renormalize。（有时更稳）
    

两版都测一下，你能在 paper 里说“我们避免把 weight 分配搞得太离谱”。

### 指标与流程

1. **Perplexity**
    

* 用 vLLM 的 `prompt_logprobs` 算 ppl：`ppl = exp(mean(-log p(x_t | x_<t)))`。[vLLM+1](https://docs.vllm.ai/en/v0.6.2/dev/sampling_params.html?utm_source=chatgpt.com)
    
* 在实验 1.1 的同一批数据上算（节省数据准备）。
    

2. **Benchmark / 跑分（代表 performance gap）**
    

* 用 lm-eval-harness（vLLM backend）：[GitHub](https://github.com/EleutherAI/lm-evaluation-harness?utm_source=chatgpt.com)
    
    * 轻量组合：HellaSwag、ARC-Challenge、GSM8K（或 MMLU subset）
        
* 注意固定 decoding（temperature=0），避免 sampling 噪声影响。
    

3. **Throughput**
    

* 用 vLLM bench/throughput 工具统计 tokens/s、requests/s；并在不同并发下测（比如 concurrency=1/4/16/32）。[vLLM+1](https://docs.vllm.ai/en/stable/api/vllm/benchmarks/throughput/?utm_source=chatgpt.com)
    

### 你预期要看到的“可发表现象”

* k 越小：吞吐上升（尤其高并发），ppl/accuracy 下降
    
* 并发越高：k 的吞吐收益越明显（因为 MoE 层更容易出现 load hotspot）

# 实验 1.3：Queue-aware 的新 Top-K policy（不考虑通信），看 ppl/跑分/吞吐

你这里最关键的问题是：**queue length 怎么定义、怎么统计**。我建议你把它定义成 **“专家侧工作量导致的排队延迟 proxy”**，工程上可观测、可控、可用于 OR/fluid。

## 1) Queue length 的可操作定义（两种都能做）

### 定义 Q1（最简单、强烈推荐作为 1.3 主实验）

把“queue length”定义成 **上一调度周期该 expert 的 routed token 数**（或其 EMA）：

* 每个 decode step（vLLM 的一个 iteration）你能得到 `a_{l,e}(t)`：这一轮在 layer l 路由到 expert e 的 token 数
    
* 用 EMA 平滑成“队列状态”：
    
    $$q_{l,e}(t) \leftarrow (1-\beta)\,q_{l,e}(t-1)+\beta\,a_{l,e}(t-1)$$
* 它不是严格的“FIFO backlog”，但在 GPU 上它是非常好的 **延迟 proxy**：谁吃到的 token 多，谁就是热点，MoE kernel 的时间往往被热点拖慢。
    

### 定义 Q2（更像真正队列，适合你后续 fluid）

把每个 expert 看成服务率为 $\mu_{l,e}$ 的 server：

$$q_{l,e}(t+1) = \max\{0, q_{l,e}(t) + a_{l,e}(t) - \mu_{l,e}\Delta t\}$$

其中 $\mu_{l,e}$ 可以用一个 microbenchmark 估出来（固定 hidden size，扫不同 token count，拟合“每 token 处理速率”）。  
这版更“运筹/流体”，但工程要多一点；你可以先用 Q1 做 feasibility，再升级到 Q2。

## 2) Queue-aware routing policy（你说的 “preference - cost”）

对每层 l，每个 token 的 router logits 记为 $z_{l,e}$。你引入 cost：

* cost（忽略通信）：$c_{l,e}(t)=\lambda\cdot \tilde q_{l,e}(t)$
    
* 调整后的 logits：
    
    $$z'_{l,e}(t)=z_{l,e}(t)-c_{l,e}(t)$$
* 再用 $z'$ 做 top-k 选择
    

**两个安全实现选项：**

* **Policy S（更稳）**：用 $z'$ 只做“选谁”，但 gate weight 仍用原始 $z$ 在选中集合内归一化（尽量保质量）
    
* **Policy A（更激进）**：选谁和权重都用 $z'$
    

建议主实验用 Policy S，paper 里再补一个消融：Policy A 更快但掉分更多。

## 3) 怎么让“queue”在实验里真的出现？

你需要“多 prompt 并发 + continuous batching”让路由热点持续存在。

**负载设计（强烈建议分两档）：**

* **Low contention**：并发=1/2（看质量几乎不变、吞吐差异小）
    
* **High contention**：并发=16/32（看 queue-aware 是否显著改善 tokens/s / tail latency）
    

在 vLLM 上你可以通过 bench 工具设置请求数、并发、输入输出长度分布来制造 hotspot（bench/throughput/latency 都能做到）。[vLLM+1](https://docs.vllm.ai/en/stable/api/vllm/benchmarks/throughput/?utm_source=chatgpt.com)

## 4) 评估指标（你这实验的“赢法”）

1. **吞吐/延迟**
    

* tokens/s、requests/s
    
* p50/p95 latency（高并发下尤其看 p95）
    

2. **质量**
    

* ppl（用 prompt_logprobs）[vLLM+1](https://docs.vllm.ai/en/v0.6.2/dev/sampling_params.html?utm_source=chatgpt.com)
    
* lm-eval accuracy（同 1.2 的 task 组合）[GitHub](https://github.com/EleutherAI/lm-evaluation-harness?utm_source=chatgpt.com)
    

3. **系统态势（写 paper 很关键）**
    

* **负载不均衡改善**：max-load / mean-load、Gini、top experts share
    
* **routing drift**：与 baseline（无 cost）相比，expert 分配变化幅度（Jaccard / KL）
    

你最终要呈现的图非常清晰：

* x 轴：$\lambda$（或者你 OR 里算出来的 cost scale）
    
* y 轴：吞吐提升 vs accuracy/ppl 下降  
    这就是你们“balance”的核心结果。

## 额外 comments：你们 idea 的风险点 & 我建议你提前规避

1. **inference-time 改路由会掉分是必然的**

* “expert load / backlog proxy”
    
* “queue length surrogate”

3. **最好加一个“只在 near-tie 时重排”的 safety 机制**
